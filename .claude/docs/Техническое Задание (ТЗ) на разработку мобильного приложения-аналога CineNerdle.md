# Техническое Задание (ТЗ) на разработку мобильного приложения-аналога CineNerdle

## 1. Введение

Данное техническое задание описывает функциональные и нефункциональные требования к мобильному приложению, являющемуся аналогом игры CineNerdle, с акцентом на соревновательный режим "Battle" (Classic 1v1). Приложение будет разработано с использованием стека Flutter для мобильного клиента и Go (чистый `net/http`) для бэкенда, с базой данных PostgreSQL.

**Цель проекта:** Создание интерактивной игры, где пользователи соревнуются в знании кино, связывая фильмы через актеров, режиссеров или композиторов. Проект также служит платформой для обучения и глубокого понимания принципов разработки.

## 2. Стек Технологий

*   **Мобильный клиент:** Flutter (Dart)
    *   Управление состоянием: BLoC/Cubit
    *   Сетевые запросы: `dio` (рекомендовано для интерцепторов)
*   **Бэкенд:** Go (чистый `net/http`)
    *   Архитектура: Clean Architecture
    *   База данных: PostgreSQL
    *   Реальное время: WebSockets (`gorilla/websocket`)
*   **Внешние API:** The Movie Database (TMDb) API

## 3. Функциональные Требования

### 3.1. Пользовательская Аутентификация и Авторизация

*   **Регистрация:** Пользователь может зарегистрироваться, используя email и пароль.
*   **Подтверждение Email:** После регистрации на указанный email отправляется письмо с уникальной ссылкой/кодом для подтверждения аккаунта. До подтверждения аккаунт считается неактивным.
*   **Вход (Login):** Пользователь может войти в систему, используя зарегистрированные email и пароль.
*   **Выход (Logout):** Пользователь может выйти из системы.
*   **Управление сессиями:** Использование JWT (JSON Web Tokens) для авторизации. Токен выдается при успешном входе и должен прикрепляться к каждому защищенному запросу.
*   **Восстановление пароля:** (Опционально, для будущих версий) Возможность восстановления пароля через email.

### 3.2. Игровой Режим "Classic Battle" (1v1)

*   **Поиск оппонента:** Пользователь может инициировать поиск случайного оппонента для игры 1v1.
*   **Начало игры:** После нахождения оппонента начинается игровая сессия.
*   **Игровой процесс:**
    *   Игра состоит из раундов, где игроки по очереди называют фильмы.
    *   Первый игрок называет любой фильм.
    *   Последующие игроки должны назвать фильм, связанный с предыдущим фильмом через общего актера, режиссера или композитора.
    *   **Проверка связи:** Бэкенд должен проверять корректность связи фильма с предыдущим (наличие общего актера/режиссера/композитора).
    *   **Таймер хода:** На каждый ход отводится ограниченное время (например, 30-60 секунд).
    *   **Пропуск хода (Skip):** Пользователь может пропустить ход. Количество пропусков ограничено за игру (например, 1-2).
    *   **Подсказки:** Пользователь может использовать подсказки для просмотра актерского состава, режиссера или композитора текущего фильма. Количество подсказок ограничено за игру (например, 1-2).
    *   **Окончание игры:** Игра заканчивается, когда один из игроков не может назвать связанный фильм в отведенное время, исчерпал пропуски/подсказки, или связь не подтверждена бэкендом.
*   **Результаты игры:** По окончании игры отображается победитель и проигравший, а также статистика игры.
*   **Реальное время:** Все действия игроков (ход, таймер, результат проверки) должны отображаться в реальном времени у обоих участников через WebSockets.

### 3.3. Управление Профилем (Базовое)

*   **Просмотр профиля:** Пользователь может просматривать свой никнейм и базовую статистику (победы/поражения).
*   **Редактирование никнейма:** Пользователь может изменить свой никнейм.

## 4. Нефункциональные Требования

*   **Производительность:** Бэкенд должен обеспечивать быструю проверку связей между фильмами (не более 1-2 секунд).
*   **Масштабируемость:** Архитектура должна предусматривать возможность горизонтального масштабирования бэкенда для обработки большого количества одновременных игр.
*   **Безопасность:** Защита от SQL-инъекций, XSS, CSRF. Хранение паролей в хешированном виде. Использование HTTPS.
*   **Надежность:** Обработка ошибок API, стабильная работа WebSockets.
*   **Удобство использования (UX):** Интуитивно понятный интерфейс, четкая обратная связь о ходе игры.

## 5. Архитектура Системы

### 5.1. База Данных (PostgreSQL)

**Таблицы:**

*   **`users`**
    *   `id` (UUID, Primary Key)
    *   `email` (VARCHAR, Unique, Not Null)
    *   `password_hash` (VARCHAR, Not Null)
    *   `nickname` (VARCHAR, Unique, Not Null)
    *   `is_verified` (BOOLEAN, Default: false)
    *   `created_at` (TIMESTAMP, Default: NOW())
    *   `updated_at` (TIMESTAMP, Default: NOW())
    *   `wins` (INTEGER, Default: 0)
    *   `losses` (INTEGER, Default: 0)

*   **`email_verifications`**
    *   `id` (UUID, Primary Key)
    *   `user_id` (UUID, Foreign Key to `users.id`, Not Null)
    *   `verification_code` (VARCHAR, Unique, Not Null)
    *   `expires_at` (TIMESTAMP, Not Null)
    *   `created_at` (TIMESTAMP, Default: NOW())

*   **`movies`**
    *   `id` (INTEGER, Primary Key, TMDb ID)
    *   `title` (VARCHAR, Not Null)
    *   `poster_path` (VARCHAR, Nullable, URL к постеру на TMDb)
    *   `release_date` (DATE, Nullable)
    *   `overview` (TEXT, Nullable)
    *   `created_at` (TIMESTAMP, Default: NOW())
    *   `updated_at` (TIMESTAMP, Default: NOW())

*   **`persons`** (Актеры, Режиссеры, Композиторы)
    *   `id` (INTEGER, Primary Key, TMDb ID)
    *   `name` (VARCHAR, Not Null)
    *   `profile_path` (VARCHAR, Nullable, URL к фото на TMDb)
    *   `created_at` (TIMESTAMP, Default: NOW())
    *   `updated_at` (TIMESTAMP, Default: NOW())

*   **`movie_person_roles`** (Связующая таблица для ролей)
    *   `movie_id` (INTEGER, Foreign Key to `movies.id`, Not Null)
    *   `person_id` (INTEGER, Foreign Key to `persons.id`, Not Null)
    *   `role` (ENUM: 'actor', 'director', 'composer', Not Null)
    *   `created_at` (TIMESTAMP, Default: NOW())
    *   Primary Key: (`movie_id`, `person_id`, `role`)

*   **`game_sessions`**
    *   `id` (UUID, Primary Key)
    *   `player1_id` (UUID, Foreign Key to `users.id`, Not Null)
    *   `player2_id` (UUID, Foreign Key to `users.id`, Not Null)
    *   `current_turn_user_id` (UUID, Foreign Key to `users.id`, Nullable)
    *   `status` (ENUM: 'waiting', 'in_progress', 'finished', 'cancelled', Not Null)
    *   `last_movie_id` (INTEGER, Foreign Key to `movies.id`, Nullable)
    *   `player1_skips_left` (INTEGER, Default: 1)
    *   `player2_skips_left` (INTEGER, Default: 1)
    *   `player1_hints_left` (INTEGER, Default: 1)
    *   `player2_hints_left` (INTEGER, Default: 1)
    *   `started_at` (TIMESTAMP, Nullable)
    *   `ended_at` (TIMESTAMP, Nullable)
    *   `winner_id` (UUID, Foreign Key to `users.id`, Nullable)
    *   `created_at` (TIMESTAMP, Default: NOW())
    *   `updated_at` (TIMESTAMP, Default: NOW())

*   **`game_moves`**
    *   `id` (UUID, Primary Key)
    *   `session_id` (UUID, Foreign Key to `game_sessions.id`, Not Null)
    *   `user_id` (UUID, Foreign Key to `users.id`, Not Null)
    *   `movie_id` (INTEGER, Foreign Key to `movies.id`, Nullable, если ход был пропуском)
    *   `move_type` (ENUM: 'movie_guess', 'skip', 'hint', Not Null)
    *   `is_valid` (BOOLEAN, Nullable, для movie_guess)
    *   `created_at` (TIMESTAMP, Default: NOW())

### 5.2. Бэкенд (Go) - Clean Architecture

**Структура папок (пример):**

```
/cmd
  /api
    main.go
/internal
  /adapters
    /repository
      user_repository.go
      movie_repository.go
      game_session_repository.go
    /tmdb
      tmdb_client.go
    /email
      email_sender.go
  /domain
    user.go
    movie.go
    person.go
    game_session.go
    game_move.go
  /usecases
    auth_usecase.go
    game_usecase.go
    profile_usecase.go
  /delivery
    /http
      auth_handler.go
      game_handler.go
      profile_handler.go
      router.go
    /websocket
      game_websocket_handler.go
/pkg
  /jwt
    jwt_manager.go
  /password
    password_hasher.go
  /errors
    app_errors.go
  /config
    config.go
```

**Основные компоненты:**

*   **`domain`:** Определяет основные сущности и бизнес-правила (структуры `User`, `Movie`, `GameSession` и т.д.).
*   **`usecases`:** Содержит бизнес-логику. Здесь происходит взаимодействие между различными репозиториями и внешними сервисами (например, `AuthUsecase` для регистрации/входа, `GameUsecase` для игровой логики).
*   **`adapters`:** Реализует интерфейсы, определенные в `usecases` и `domain`. Включает:
    *   **`repository`:** Взаимодействие с базой данных (PostgreSQL).
    *   **`tmdb`:** Клиент для работы с TMDb API.
    *   **`email`:** Отправка email (например, для подтверждения).
*   **`delivery`:** Точка входа для внешних запросов.
    *   **`http`:** REST API для аутентификации, профиля, поиска игр.
    *   **`websocket`:** Обработка игровых сессий в реальном времени.
*   **`pkg`:** Общие утилиты (JWT, хеширование паролей, обработка ошибок, конфигурация).

**Эндпоинты (REST API):**

*   `POST /api/v1/auth/register` - Регистрация пользователя
*   `GET /api/v1/auth/verify-email?code={code}` - Подтверждение email
*   `POST /api/v1/auth/login` - Вход пользователя (возвращает JWT)
*   `GET /api/v1/profile` - Получение данных профиля (требуется JWT)
*   `PUT /api/v1/profile` - Обновление профиля (требуется JWT)
*   `POST /api/v1/game/find-match` - Поиск оппонента (требуется JWT)

**WebSockets:**

*   `GET /ws/game/{session_id}` - Подключение к игровой сессии (требуется JWT)
    *   Сообщения для обмена ходами, состоянием таймера, результатами проверки.

### 5.3. Мобильный Клиент (Flutter)

**Структура BLoC (пример):**

*   **`AuthBloc`:** Управление состоянием аутентификации (залогинен/не залогинен, регистрация, вход, выход, подтверждение email).
*   **`ProfileBloc`:** Управление состоянием профиля пользователя (данные, статистика, редактирование).
*   **`GameSearchBloc`:** Управление состоянием поиска оппонента.
*   **`GameBloc`:** Управление состоянием активной игровой сессии (текущий ход, таймер, фильмы, подсказки, пропуски).

**Сетевые запросы:** Использование `dio` для всех HTTP-запросов. `dio` будет настроен с интерцептором для автоматического добавления JWT-токена в заголовки запросов.

## 6. Игровая Логика и Взаимодействие с TMDb

1.  **Получение данных о фильме:** При первом запросе фильма (или при поиске) бэкенд обращается к TMDb API для получения основной информации (название, постер, дата выхода) и списка актеров/режиссеров/композиторов.
2.  **Кэширование в PostgreSQL:** Полученные данные о фильме и связанных с ним персонах (актерах, режиссерах, композиторах) сохраняются в локальной базе данных (`movies`, `persons`, `movie_person_roles`). Это позволяет избежать повторных запросов к TMDb и ускорить проверку связей.
3.  **Проверка связи фильма:** Когда игрок предлагает новый фильм, бэкенд выполняет следующие шаги:
    *   Проверяет, существует ли фильм в локальной БД. Если нет, запрашивает у TMDb и кэширует.
    *   Получает список всех актеров, режиссеров и композиторов для *предыдущего* фильма из `movie_person_roles`.
    *   Получает список всех актеров, режиссеров и композиторов для *нового* фильма из `movie_person_roles`.
    *   Сравнивает эти списки на наличие общих персон. Если найдена хотя бы одна общая персона (с любой ролью), связь считается установленной.
    *   **Важно:** Для оптимизации запросов к БД можно использовать сложные SQL-запросы с `JOIN` и `INTERSECT` для поиска общих персон.
4.  **Обработка подсказок:** При использовании подсказки, бэкенд отправляет клиенту список актеров/режиссеров/композиторов текущего фильма.

## 7. План Разработки (Дорожная Карта)

Рекомендуется итеративный подход:

### Фаза 1: Базовый Бэкенд и Аутентификация

1.  Настройка проекта Go, PostgreSQL.
2.  Реализация Clean Architecture (базовые слои).
3.  Разработка модуля аутентификации (регистрация, подтверждение email, вход, JWT).
4.  Тестирование REST API с помощью Postman/Insomnia.

### Фаза 2: Базовый Фронтенд и Аутентификация

1.  Настройка проекта Flutter.
2.  Реализация `AuthBloc` и UI для регистрации/входа.
3.  Интеграция с бэкендом (использование `dio`).
4.  Проверка подтверждения email.

### Фаза 3: Интеграция с TMDb и Кэширование

1.  Получение API-ключа TMDb (если еще нет).

3.  Реализация логики кэширования фильмов и персон в PostgreSQL.
4.  Создание эндпоинта для поиска фильмов (для отладки).

### Фаза 4: Игровая Логика (Core Battle)

1.  Разработка `GameUsecase` в Go для управления игровой логикой.

3.  Разработка логики проверки связей между фильмами.
4.  Реализация `GameSearchBloc` и `GameBloc` во Flutter.

### Фаза 5: Дополнительный Функционал Игры

1.  Реализация пропусков хода и подсказок.
2.  Добавление таймера хода.

### Фаза 6: Улучшения и Развертывание

4.  Настройка CI/CD (опционально, для продвинутых).

## 8. Важные Замечания

*   **API-ключ TMDb:** Для работы с TMDb API необходимо получить бесплатный ключ на [The Movie Database (TMDb)](https://www.themoviedb.org/documentation/api).
*   **SMTP-сервер:** Для отправки писем подтверждения email потребуется доступ к SMTP-серверу. Для разработки можно использовать сервисы типа [Mailtrap](https://mailtrap.io/) или [Mailgun](https://www.mailgun.com/).
*   **Локальная разработка:** Начинать следует с локальной разработки, используя Docker Compose для запуска PostgreSQL и Go-сервера.
*   **Тестирование:** Важно писать юнит- и интеграционные тесты для бэкенда и виджет-тесты для Flutter.
